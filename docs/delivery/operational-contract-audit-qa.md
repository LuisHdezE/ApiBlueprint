# BP-ADOPT-004 — Operational contract and audit QA

## Objective

Close the executable Postman contract gap and prove semantic audit behavior for APIs generated by ApiBlueprint, while preserving OpenAPI as the formal API contract and without changing production.

## Canonical operational contract

The repository owns these artifacts:

- `postman/ApiBlueprint.generated.postman_collection.json`: executable Postman collection.
- `postman/ApiBlueprint.local.postman_environment.json`: non-secret local environment. Runtime bearer tokens start empty and are populated only during execution.
- `postman/operation-coverage.json`: one-to-one mapping from every implemented Master OpenAPI `operationId` to its canonical Postman request and semantic audit event.
- `deployment/operational-contract-manifest.json`: deterministic manifest used to export the generated API exercised by CI.

Master OpenAPI remains the formal contract. `tests/Feature/PostmanOperationalContractTest.php` rejects missing or duplicated operation coverage and verifies method/path reconciliation against OpenAPI.

## Runtime acceptance

`scripts/run-postman-operational-contract.sh` performs the acceptance against a real exported solution:

1. starts the root ApiBlueprint runtime;
2. exports the governed seven-operation API as a ZIP;
3. installs the generated project and prepares an isolated SQLite database;
4. seeds only synthetic `example.test` users and a synthetic product;
5. starts the generated API locally;
6. executes Newman `6.2.1` against that runtime;
7. produces a sanitized Newman summary and deletes the raw Newman JSON;
8. validates the generated `storage/logs/audit.jsonl` against the canonical semantic-event coverage;
9. publishes only the sanitized summaries as CI artifacts.

CI #111 (`35924101353`) on commit `2dd30646036dfc56975e80f0969bc2808271db61` completed successfully. The sanitized report recorded 15 requests, 36 assertions and zero failures. Positive behavior, authentication, authorization, validation, not-found handling and idempotency replay were exercised.

## Semantic audit contract

When `governance.audit=true`, `OperationalContractBlueprintExporter` augments the generated ZIP with:

- `config/apiblueprint_audit.php`, mapping generated route names to canonical feature `audit_events`;
- an append-oriented JSONL audit sink at `storage/logs/audit.jsonl`;
- semantic audit middleware;
- `tests/Feature/AuditSemanticContractTest.php`, which travels with the generated project.

Each semantic record contains the event code, timestamp, route, method/path, HTTP status, outcome, correlation ID, actor ID when available and target ID when available. Request bodies and request headers are not copied into the audit event.

The durable sink recursively redacts sensitive keys such as passwords, tokens, authorization values, secrets and hashes, and also rejects direct Bearer-value persistence. Generated QA explicitly injects synthetic secret-looking values to prove that they do not survive in the audit record.

The CI #111 audit report observed all seven canonical event codes:

- `audit.auth.login`
- `audit.auth.logout`
- `audit.users.list`
- `audit.users.show`
- `audit.users.create`
- `audit.products.list`
- `audit.products.show`

The report contained no missing event codes, malformed semantic records, empty correlation IDs or sensitive markers.

## Negative and cross-cutting coverage

The operational collection includes explicit scenarios for:

- invalid login → 401;
- unauthenticated admin operation → 401;
- authenticated non-admin admin operation → 403;
- missing idempotency key → 400;
- invalid create-user payload → 422;
- missing product → 404;
- successful idempotency replay with `X-Idempotent-Replay: true`.

These checks complement, rather than replace, the generated PHPUnit suites and OpenAPI validation.

## Deliberate boundaries

BP-ADOPT-004 does **not** claim that every security threat has been tested. `api.security_qa` remains pending until a complete Blueprint security-QA evidence set exists.

Audit retention is also intentionally separate. `audit.retention_policy` remains pending because this checkpoint proves semantic emission, append-oriented storage and secret exclusion, not organizational retention duration or archival/deletion policy.

Authentication/authorization failures that terminate before the route audit middleware executes are covered by Postman as security behavior, but are not represented as semantic route audit events in this checkpoint. The semantic event acceptance therefore targets operations that reach the governed route middleware.

No production deployment or promotion is part of BP-ADOPT-004.
