# Audit retention, access and tamper policy

## Scope

This policy applies to durable business/security audit produced by APIs generated by ApiBlueprint. It is deliberately separate from ordinary technical logs.

The **ApiBlueprint root composer** does not currently emit or persist a durable business/security audit store because it has no root accounts, customer business mutations or authoritative business database. Root operational logs follow hosting/runtime logging policy and are not promoted to durable business audit by this document.

## Generated API reference behavior

When `governance.audit=true`, the generated reference runtime emits semantic audit records to an append-oriented JSONL sink. Normal generated CRUD/application flows do not expose update/delete operations for those records.

The reference runtime does **not** silently delete, rotate or archive audit records. This is intentional: a reusable generator cannot choose a lawful/appropriate retention period for every consumer domain.

## Production retention decision

Before a generated API with audit enabled is released to production, the deployment/consumer must explicitly record all of the following:

- retention duration or legal/business rule that determines it;
- active storage and archive location;
- rotation/archive mechanism;
- deletion/disposal mechanism after the approved period;
- roles/identities permitted to read/export audit records;
- administrative identities permitted to manage retention/storage;
- incident/legal-hold override when applicable;
- restore/search procedure needed for accountable investigation.

A production deployment must not interpret "no automatic deletion" as a universal requirement for indefinite retention.

## Reference/demo/CI policy

Audit data created only by automated tests, CI or local demos is synthetic and non-authoritative. It may be destroyed with the ephemeral workspace after the run. Sanitized CI evidence may be retained according to the CI provider/repository artifact policy because it contains summaries, not bearer tokens/passwords or raw audit payloads.

## Access policy

Durable audit is server-side authoritative evidence.

- Application end users do not receive direct filesystem/storage access to the sink.
- Read/export access is granted only to operational/security/administrative roles justified by the consumer deployment.
- Ordinary business CRUD code must not mutate or delete existing audit records.
- Client telemetry must not become an undocumented competing durable audit store.

## Sanitization policy

Passwords, password hashes, bearer/authorization values, access/refresh/reset tokens, API keys, secrets and equivalent credential material must not be retained in durable audit.

Generated semantic audit uses minimum accountable fields and recursive redaction. BP-ADOPT-004 runtime acceptance remains the executable proof that canonical event codes, correlation and sensitive-value exclusion work.

## Tamper and administrative override policy

The reference JSONL sink is append-oriented at application level, but filesystem administrators remain privileged. Deployments requiring stronger immutability must move audit to storage with controls appropriate to their risk, such as append-only/WORM/external audit infrastructure.

Any administrative override that removes/rewrites audit data before the approved retention boundary must be governed outside ordinary application flows and, where the deployment supports it, leave its own accountable administrative evidence.

## Export/search policy

The reference implementation does not add a public audit search/export API automatically. Consumers that require search/export must introduce an explicitly authorized operation and preserve the same sanitization/access boundary. A convenience endpoint must never expose the raw audit sink anonymously.

## Completion and revalidation

This policy satisfies the ApiBlueprint architecture baseline by defining ownership, access, sanitization, retention decision boundaries and deletion/archive responsibility without pretending one duration fits every generated domain.

A consumer-specific release remains responsible for choosing and evidencing its concrete duration/mechanism. Changes to the audit sink, event schema, access model or secret-redaction rules require audit/security revalidation.
